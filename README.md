# V Slot

Native Android social casino / simulated slots app.

## Store-Ready Inputs

The repository intentionally does not contain production secrets or fake release data.

Before a production release, provide every release value through environment variables in protected CI. Release configuration deliberately rejects `-P` and `local.properties` so provenance can bind the exact inputs without hidden machine-local overrides:

```properties
V_SLOT_PRIVACY_POLICY_URL=
V_SLOT_SUPPORT_EMAIL=
V_SLOT_DEVELOPER_LEGAL_NAME=
V_SLOT_APPMETRICA_API_KEY=
V_SLOT_APPMETRICA_API_KEY_SHA256=
V_SLOT_FIREBASE_PROJECT_ID=
V_SLOT_FIREBASE_APP_ID=
V_SLOT_DATA_SAFETY_REVIEWED_VERSION_CODE=
V_SLOT_DATA_SAFETY_EVIDENCE_FILE=
V_SLOT_DATA_SAFETY_EVIDENCE_SHA256=
V_SLOT_DATA_SAFETY_RAW_EVIDENCE_FILE=
V_SLOT_DATA_SAFETY_RAW_EVIDENCE_SHA256=
V_SLOT_ASSET_RIGHTS_REVIEWED_VERSION_CODE=
V_SLOT_ASSET_RIGHTS_EVIDENCE_FILE=
V_SLOT_ASSET_RIGHTS_EVIDENCE_SHA256=
V_SLOT_SAMSUNG_QA_EVIDENCE_FILE=
V_SLOT_SAMSUNG_QA_EVIDENCE_SHA256=
V_SLOT_PROCESS_DEATH_EVIDENCE_FILE=
V_SLOT_PROCESS_DEATH_EVIDENCE_SHA256=
V_SLOT_FRAME_METRICS_EVIDENCE_FILE=
V_SLOT_FRAME_METRICS_EVIDENCE_SHA256=

```

`V_SLOT_SUPPORT_EMAIL` and `V_SLOT_DEVELOPER_LEGAL_NAME` are the exact public Play Console contact and legal identity; the same legal name must appear in the published privacy policy. `V_SLOT_APPMETRICA_API_KEY_SHA256` pins the intended production AppMetrica key without duplicating it. `V_SLOT_FIREBASE_PROJECT_ID` and `V_SLOT_FIREBASE_APP_ID` pin the intended Firebase backend. Set `V_SLOT_DATA_SAFETY_REVIEWED_VERSION_CODE` to the current `versionCode` only after the final release scope, SDK/data flows, production dashboards, privacy policy, and Play Console Data Safety answers have been reviewed; changing `versionCode` invalidates the confirmation. `V_SLOT_DATA_SAFETY_EVIDENCE_FILE` must point to the completed schema-v1 sign-off based on `docs/store/DATA_SAFETY_EVIDENCE_TEMPLATE.json`, while `V_SLOT_DATA_SAFETY_EVIDENCE_SHA256` pins its exact bytes. `V_SLOT_DATA_SAFETY_RAW_EVIDENCE_FILE` must be the pinned wrapper ZIP containing that exact manifest, the raw pcapng, Play Console CSV, privacy-policy HTML snapshot, and an inner evidence ZIP containing the same three raw files; the manifest hashes are recalculated from those bytes. `V_SLOT_ASSET_RIGHTS_REVIEWED_VERSION_CODE` and the checksum-pinned `V_SLOT_ASSET_RIGHTS_EVIDENCE_FILE` bind an authorized media/name rights review to the current version, release commit, and `docs/legal/ASSET_PROVENANCE_INVENTORY.json`; use `docs/legal/ASSET_RIGHTS_EVIDENCE_TEMPLATE.json` only as an incomplete template. `V_SLOT_RELEASE_CERT_SHA256` is the expected SHA-256 fingerprint of the Play upload certificate; `verifyStoreReadiness` rejects any mismatch. `V_SLOT_ANDROID_PLATFORM_36_JAR_SHA256`, `V_SLOT_ANDROID_BUILD_TOOLS_36_AAPT2_SHA256`, and `V_SLOT_ANDROID_BUILD_TOOLS_36_DEXDUMP_SHA256` pin the reviewed Linux CI toolchain bytes; update them only after reviewing an intentional SDK package change.

`V_SLOT_OSV_SCAN_EVIDENCE_FILE` is generated by the protected production workflow after its pinned reusable OSV job succeeds. It is bound to the release commit, workflow run, scanner revision, and exact reviewed inventory; do not hand-author it as a standing Environment value.

Signing passwords are accepted only from environment variables so they cannot be exposed through Gradle `-P` arguments, `local.properties`, or command echoes:

```text
V_SLOT_RELEASE_STORE_PASSWORD
V_SLOT_RELEASE_KEY_PASSWORD
```

Do not paste dummy URLs, fake analytics keys, or placeholder signing credentials. Leave these values unset until the real production inputs are available.

For production AppMetrica Push via FCM, place the real `google-services.json` in `app/src/release/`. The file is gitignored and must contain an Android client for `com.vslot.app`.

Debug and QA use independent, opt-in backend namespaces. Without their inputs they build with `NoOpAnalyticsTracker` and Firebase disabled. To exercise a non-production backend, use `V_SLOT_DEBUG_APPMETRICA_API_KEY` with `app/src/debug/google-services.json` for `com.vslot.app.debug`, or `V_SLOT_QA_APPMETRICA_API_KEY` with `app/src/qa/google-services.json` for `com.vslot.app.qa`. Never reuse production AppMetrica or Firebase projects for these variants.

AppMetrica is not activated until the player opts in to analytics or separately enables push. Its initial provider configuration disables data sending, advertising identifiers, location, crash/native-crash reporting, automatic sessions, automatic app-open events, ANR monitoring, and revenue tracking. A player can revoke analytics consent at any time. Revocation disables the runtime first and is mirrored to a synchronous fail-closed guard, so a transient persistence failure cannot silently re-enable collection on restart. The production privacy policy and Google Play Data safety form must describe the actual AppMetrica and push configuration and data flow.
The build also excludes AppMetrica's optional ad-revenue, billing, identifiers, location, screenshot, App Set ID, ID sync, and native-crash modules because V Slot does not use those data paths.

Player economy state uses one checksummed `DataStore<PlayerStateCheckpoint>` record in `noBackupFilesDir`. Balance, free-spin balances and locked stakes, settlement/refund journals, presentation replay, settings, and the monotonic revision are committed by one `updateData` transaction. Existing Preferences DataStore and legacy checkpoint files are read only by a one-shot migration; after migration they are never used as competing writers or rollback sources. A corrupt transactional primary fails closed instead of silently restoring an older economy revision. Daily-bonus claims also preserve the greatest persisted claim timestamp as a wall-clock rollback floor, so moving the device clock forward to claim and then backward cannot reopen the reward after restart.

## Compliance Rules

- No real-money gambling.
- No cash prizes, withdrawals, NFT rewards, coupons, deposits, or external real-money casino links.
- Virtual coins are entertainment-only and have no real-world value.
- Push copy must only mention daily bonus reminders or game updates.

## Build

Prerequisites:

- Temurin JDK 17.0.19+10 (`JAVA_HOME` must point to that installation for production builds).
- Android SDK Platform 36, Build Tools 36.0.0, and current Platform Tools installed.
- An accepted Android SDK license set and an executable checked-in Gradle wrapper.
- For asset regeneration only: Python 3.9.6 and Pillow 11.3.0 with FreeType 2.13.3 and libwebp 1.5.0. `tools/vslot_asset_toolchain.py` rejects any other raster environment.

From a clean checkout, verify the toolchain before building:

```bash
java -version
${ANDROID_HOME:-$HOME/Library/Android/sdk}/platform-tools/adb version
./gradlew --version
```

```bash
./gradlew test
./gradlew lintDebug
./gradlew assembleDebug
./gradlew bundleRelease
./gradlew :app:verifyStoreRelease
./gradlew :app:verifyStoreReadiness
./gradlew :app:verifyPhysicalSamsungEvidence
./gradlew :app:verifySourceWebpEncoding
./gradlew :app:verifyReleaseResourceSize
./gradlew :app:archiveReleaseMapping
./gradlew verifyWorkspaceSecurity
./gradlew verifyReleaseProvenance
```

Run `verifyStoreRelease` when the real production inputs are available; every terminal release artifact task invokes the same release tests, lint, security, resource, and signing-readiness lifecycle automatically.
Run `verifyStoreReadiness` only when the real production AppMetrica, Firebase, Privacy Policy, support/legal identity, signing inputs, expected upload-certificate SHA-256, current-version Data Safety and asset-rights evidence, all three physical-Samsung evidence manifests, and their raw evidence archive are available.
Run `verifySourceWebpEncoding` after adding visual assets; large lossless WebP files must be visually reviewed and encoded as high-quality lossy WebP before release.
Run `verifyReleaseResourceSize` after intentional visual asset changes; release artifact tasks run it automatically and reject an optimized resource archive over 64 MiB or any single resource over 1 MiB.
Run `archiveReleaseMapping` for every candidate build and retain `app/build/outputs/diagnostics/release/v-slot-<version>-<code>-r8-mapping.zip` with the published artifact. It requires a committed, clean Git worktree and includes `release-provenance.txt` with the exact commit, tree, Firebase config hash, release-configuration hash, and SHA-256 digests of the Android 36 platform JAR, build-tools 36.0.0 `aapt2`, and reviewed bundletool JAR. After building, pinned bundletool 1.18.3 validates that exact AAB, dumps its delivered base manifest, and rejects a wrong package, `debuggable`/`testOnly`, or QA components. `bundleRelease` also writes `app/build/reports/release-security/release-artifact-evidence.txt`, binding the signed AAB and bundletool outputs to the upload certificate, provenance, security, tests, lint, merged manifest, lock state, verification metadata, and R8 archive. Upload `mapping.txt` to the crash-reporting/store console for that exact version.
Run `verifyWorkspaceSecurity` before staging or publishing changes; release artifact tasks run it automatically and scan reachable Git history, commit/tag messages, index, and worktree candidates. Before a first commit it reports `INCOMPLETE`, so production release evidence cannot claim full history coverage.

Every production candidate must come from a committed, clean Git worktree in protected CI. Retain the signed AAB, its SHA-256, upload-certificate SHA-256, `release-provenance.txt`, dependency lock and verification metadata hashes, R8 mapping archive, test/lint reports, physical-Samsung evidence, privacy/Data safety sign-off, asset-rights sign-off, and release notes under the same `versionCode`. Keystore material stays in protected secret storage; document its owner, backup, access policy, and rotation/recovery procedure outside this repository.

The checked-in `Android CI` workflow runs the complete non-production verification graph for pull requests, pushes to `main`, and a weekly advisory refresh. A pinned OSV-Scanner job checks the reviewed `osv-scanner-custom.json`, generated only from the resolved `releaseRuntimeClasspath`, and blocks both CI and production release on known vulnerabilities. Gradle verification rejects that inventory if it differs byte-for-byte from the current runtime graph, avoiding both stale scans and false release failures from build/test tooling that is not packaged in the app. Dependabot separately monitors Gradle build dependencies and pinned GitHub Actions. The manual `Production Release` workflow accepts only protected `main`, materializes signing and Firebase files only for the build, runs the fail-closed `bundleRelease` graph, generates GitHub artifact attestations for the signed AAB and its security/raw-device evidence, and uploads the complete evidence set. All third-party workflow actions are pinned to immutable commit SHAs.

After an intentional dependency change, regenerate both states with the required build graph and review every checksum/version diff before accepting it:

## Samsung QA

Run connected UI tests on a physical Samsung device with an explicit serial:

```bash
tools/qa_samsung_connected_tests.sh SAMSUNG_TEST_SERIAL_0001
```

The script runs seven mandatory stages against a release-like minified and resource-shrunk APK that keeps the debug-only QA hooks and uses the Android debug signing key: portrait smoke; first-launch, scalable dialogs, legal copy, and notices at `font_scale=2.0`; compact portrait Settings at `720x1280`/`320dpi`; compact slot/home coverage at `720x1080`/`320dpi` in both forced landscape rotations; and the full 63-test connected suite at Surface rotation 90 (`user_rotation=1`) and 270 (`user_rotation=3`). It verifies WindowManager display rotation, logical dimensions, and locked rotation settings both before and after every connected stage, rejects emulators, requires every focused stage to pass without skipped tests, and requires each full-suite stage to report exactly 63 tests with the five profile-specific skips. It archives all XML reports under the evidence directory and checks that the canonical QA APK payload SHA-256 remains unchanged across all seven stages. It restores and verifies the exact original `wm size`, density, font scale, rotation, and power settings through `trap`, and writes a redacted schema-v6 JSON evidence manifest with both the exact signed-file hash and canonical payload hash, Git commit, and test/skip counts for every stage under ignored `qa/screenshots/evidence/`. It refuses to mutate the device unless all restorable state was captured, or to run if another Samsung QA process is already using the same device. It also force-stops the known conflicting `com.dragonslots` QA package before launching V Slot tests; set `V_SLOT_SKIP_CONFLICT_STOP=1` to skip that cleanup.
The device must appear in `adb devices -l` with state `device`; authorize USB debugging and unlock the phone before running the script.

Run the isolated deterministic slot smoothness check with an explicit device serial:

```bash
ANDROID_SERIAL=SAMSUNG_TEST_SERIAL_0001 tools/qa_slot_frame_metrics.sh
```

It runs only `SlotFrameMetricsTest`, reports frame count, p50, p95, p99, maximum frame time, the rate above 32 ms, and the refresh-rate-aware missed-deadline rate, and writes a log plus a schema-v2 redacted JSON manifest with the Git commit, signed QA APK hash, and canonical payload hash under `qa/frame-metrics/`. The physical-Samsung profile requires p95 at or below 50 ms, p99 and maximum frame time at or below 100 ms, no more than 10% of frames above 32 ms, and no more than 20% missed display deadlines. Emulator runs enforce only catastrophic-regression ceilings of 250 ms p95 and 500 ms maximum; p99, jank, and missed-deadline rates remain diagnostic because software-rendering timing is not release-performance evidence. An explicitly supplied emulator serial is accepted for this catastrophic-regression check, but its result never counts as physical-Samsung release evidence.

Run the host-driven durable settlement check separately on an unlocked physical Samsung:

```bash
ANDROID_SERIAL=SAMSUNG_TEST_SERIAL_0001 tools/qa_process_death_recovery.sh
```

It commits a deterministic paid spin without settling it, kills the release-like QA process through ActivityManager, verifies one recovered settlement, requires a logged first draw of the result dialog before production code acknowledges the presentation, then kills and launches the process again to prove the balance is not credited twice. Schema-v5 redacted JSON evidence records the Git commit, exact signed QA APK hash, canonical payload hash, three distinct process IDs, fixture arithmetic, and exactly-once checks under `qa/process-death/evidence/`. The same host sequence can be exercised on an explicitly selected AVD with `V_SLOT_ALLOW_EMULATOR_QA=1`; the resulting manifest is marked `emulator` and is never physical-Samsung release evidence.

For a production candidate, pin each of the three JSON files by SHA-256 in the protected `production` Environment. The connected, frame-metrics, and process-death manifests use schemas v6, v2, and v5 respectively. `verifyPhysicalSamsungEvidence` rebuilds the QA APK from release `HEAD`, requires all manifests to name that exact commit, canonical APK payload digest, and one hashed physical Samsung serial, rejects emulator or incomplete results, enforces the exact expected `classname#testcase` IDs, rejects testcase-level failure/error/skipped nodes even when counters lie, and enforces frame limits. It then archives the validated manifests under `app/build/reports/release-security/physical-samsung/`. The per-file `sha256` identifies the exact signed APK used on the device; `payload_sha256`, generated by `tools/apk_payload_sha256.sh`, binds equivalent APK contents across probabilistic signing blocks or different debug keystores. The signed AAB evidence includes a digest of that archive. Until these physical runs exist for the committed candidate, every release artifact task fails closed. Text evidence proves content integrity, not hardware origin; production approval must obtain it from a trusted device-lab job and bind that job's attestation to the commit and APK payload.

After all three runs, package the selected manifests with their matching XML and raw logs:

```bash
tools/package_physical_samsung_evidence.sh CONNECTED.json PROCESS_DEATH.json FRAME_METRICS.json physical-samsung-raw-evidence.zip
```

Pin this ZIP through `V_SLOT_PHYSICAL_SAMSUNG_RAW_EVIDENCE_FILE` and `V_SLOT_PHYSICAL_SAMSUNG_RAW_EVIDENCE_SHA256`. The release validator requires byte-identical copies of the three pinned manifests, exact passing XML counts for all seven connected stages, bounded ZIP entries, and commit/APK-payload markers in both raw device logs.

All Samsung host scripts share a per-device lock and refuse to run concurrently.

When you intentionally want V Slot to take the Samsung device from an old `Dragon Slots` QA loop, run:

```bash
V_SLOT_STOP_EXTERNAL_QA=1 tools/qa_samsung_connected_tests.sh SAMSUNG_TEST_SERIAL_0001
```
